# Phase 2: Server-Side Wallet System Removal

**Date:** 2026-07-31  
**Status:** ✅ Complete  
**Migration Phase:** Phase 2 (On-device wallets via BDK)

## Overview

This migration removes the server-side wallet system for reserve deposits, completing the transition to on-device wallet management using BDK in mobile clients. The admin funding system now works with addresses registered by mobile clients, rather than generating addresses server-side.

## Problem Statement

- **Before:** Server generated Bitcoin addresses via `L1::ReserveReceiveAddressService` and `L1::UserWallet`
- **Issue:** Mobile clients now manage wallets on-device (Phase 2), but admin funding still tried to use server-side address generation
- **Error:** "No user found with that receive address" when admin tried to fund users

## Architecture Changes

### What Was Removed

1. **`L1::ReserveReceiveAddressService`** - Server-side address generation
2. **`L1::DepositReserveService`** - Server-side deposit handling via bitcoind
3. **`L1::SyncReserveBalanceService`** - Synced balance from bitcoind to DB
4. **`L1::ReserveBalance`** module - Balance querying from bitcoind

### What Was Changed

#### 1. Reserve API (`Api::V1::ReserveController`)

**Before:**
- `GET /reserve` - Generated address via `ReserveReceiveAddressService`
- `POST /reserve/sync` - Synced balance from bitcoind wallet

**After:**
- `GET /reserve` - Returns stored address (or null if not registered)
- `PUT /reserve/update_address` - Mobile clients register their BDK address
- `POST /reserve/sync` - Now a no-op (mobile clients sync via BDK)

#### 2. Admin Funding Controllers

**Admin Web UI** (`Admin::ReserveDepositsController`):
- Changed from looping through all users calling `ReserveReceiveAddressService`
- Now looks up user by `reserve_receive_address` column
- Uses `L1::FundReceiveAddressService` (which doesn't require server wallets)

**Admin API** (`Api::V1::Integration::AdminFundReservesController`):
- Changed from `DepositReserveService` to `FundReceiveAddressService`
- Returns error if user hasn't registered an address yet

#### 3. Fund Receive Address Service

Updated to not use `UserWallet` for balance sync:
- Balance now updated directly in database when funding
- No longer calls `UserWallet.for(user).sync_balance_to_account!`

#### 4. User-Facing Reserve Deposits

Web UI (`ReserveDepositsController`) updated to:
- Show stored address instead of generating one
- Use `FundReceiveAddressService` instead of `DepositReserveService`
- Disable funding if no address registered (prompts to use mobile app)

### What Was Kept

**`L1::UserWallet`** - Still needed for PoC DLC operations:
- DLC contract funding (borrower/investor inputs)
- PSBT signing for DLC transactions
- Escrow identity keys
- Coin selection

**Status:** Will be replaced in Phase 3 (DLC on device)

**`bitcoind_wallet_name` column** - Still needed for DLC wallets until Phase 3

## Mobile Client Changes

### New API Flow

1. **Wallet Creation:**
   ```dart
   // Mobile creates wallet via BDK
   final address = await bdkWallet.getReceiveAddress();
   
   // Registers with server
   await api.updateReserveAddress(address);
   ```

2. **Admin Funding:**
   - Admin pastes address in web UI
   - Server looks up user by `reserve_receive_address`
   - Funds from exchange wallet
   - Updates balance in database

3. **Balance Updates:**
   - Mobile: BDK syncs with Electrum (on-device)
   - Server: Balance updated when admin funds

### Integration Points

**`WalletState.createWallet()`** now:
1. Creates BDK wallet on-device
2. Gets receive address
3. Automatically registers address with server via `api.updateReserveAddress()`
4. Silently continues if server registration fails (user can still use wallet)

## Migration Path

### For Existing Users

**Development/Test:**
1. Existing users have no `reserve_receive_address` set
2. First mobile wallet creation registers address
3. Admin funding works after registration

**Production (Future):**
- Migration script not needed (column already exists)
- Users create mobile wallets naturally as they onboard

### For Developers

**Old Pattern (Removed):**
```ruby
# ❌ No longer works
L1::ReserveReceiveAddressService.ensure!(user: user)
L1::DepositReserveService.call(user: user, amount_sats: sats)
```

**New Pattern:**
```ruby
# ✅ Phase 2
address = user.btc_account.reserve_receive_address
raise "No address registered" unless address.present?

L1::FundReceiveAddressService.call(
  address: address,
  amount_sats: sats
)
```

## Benefits

1. **Simplified Architecture:** No server-side wallet management for reserves
2. **True Self-Custody:** Users control their reserve keys on-device
3. **Scalability:** No bitcoind wallet per user for reserves
4. **Security:** Private keys never touch the server
5. **Clear Separation:** Reserve system (Phase 2) vs DLC system (Phase 3)

## Limitations & Future Work

### Current Limitations

1. **DLC Still Uses Server Wallets:** `L1::UserWallet` still needed for DLC operations
2. **No Migration for Existing Balances:** Old server-side wallets not automatically transferred
3. **Admin Dependency:** Users still need admin to fund reserves (test environment)

### Phase 3 (Future)

- Remove `L1::UserWallet` entirely
- DLC signing on-device via mat-dlc
- Remove `bitcoind_wallet_name` column
- Full self-custody including DLC operations
